# Архитектура

## Требования и как они закрыты

| Требование | Решение |
|---|---|
| Производительность | Go (компилируемый, низкое потребление памяти, тысячи RPS на ядро), pgx без ORM, keyset-пагинация вместо OFFSET, частичные индексы под публичный каталог, trigram-индекс для поиска |
| Выдерживать большой поток | API без состояния → горизонтальное масштабирование за балансировщиком; общее состояние только в PostgreSQL и Redis; лимиты запросов в Redis работают на всех инстансах сразу; пул соединений с лимитом; таймауты на каждый запрос и `statement_timeout` в БД |
| Надёжность | Транзакции на каждую бизнес-операцию, инварианты в самой БД (CHECK, UNIQUE, FK, триггеры append-only), graceful shutdown, healthz/readyz для оркестратора, ежедневные зашифрованные бэкапы + PITR, автоматическая проверка восстановления в CI |
| Быстрая диагностика | JSON-логи (одна строка на запрос) с `request_id`, который возвращается клиенту в ответе и заголовке `X-Request-ID`; метрики Prometheus (`/metrics`: RPS, латентность, коды по роутам); pprof на внутреннем порту; стабильные коды ошибок |
| Безопасность | см. раздел «Безопасность» |

## Компоненты

```
 Клиент (Next.js) ──HTTPS──► Балансировщик/CDN ──► API (Go, N инстансов) ──► PostgreSQL 16 (primary + реплика)
                                                     │            │
                                                     │            └──► Redis 7 (лимиты, OTP, кэш)
                                                     └──► S3/MinIO (приватный бакет: фото товаров, клиентов, мест доставки)
 Бэкапы: pg_dump (ежедневно, age-шифрование) + WAL-G (непрерывно, PITR) ──► отдельный S3-бакет
```

- **API** — один бинарник, `internal/<модуль>` на каждую предметную область. Модуль = хендлеры + SQL. Общие соглашения — `internal/httpx`.
- **PostgreSQL** — единственный источник истины. Деньги в тийинах (`BIGINT`), время в `timestamptz`, id — UUID.
- **Redis** — только для временных данных (OTP, счётчики лимитов). Потеря Redis не теряет бизнес-данных.
- **S3** — бакет `boutique-media`. Префикс `pub/` (фото товаров, логотипы) публичный и отдаётся через CDN по постоянным URL, поэтому кэшируется. Префикс `priv/` (фото клиентов, фото мест доставки) закрыт, доступ только по подписанной ссылке на 15 минут.
- **Просмотры товаров** считаются в Redis и сбрасываются в БД раз в 30 с одним запросом, поэтому популярный товар не создаёт блокировок строк. Карточка товара читается только через SELECT и может уходить на реплику или в кэш.
- **AI-примерка** — очередь на PostgreSQL (`SELECT … FOR UPDATE SKIP LOCKED` + аренда задания), воркер `api worker`, сменные AI-провайдеры, биометрия в отдельном хранилище в Узбекистане. Подробно — [TRYON.md](TRYON.md).
- **Другие фоновые задачи** (импорт Excel, вебхуки Click/Payme) — тот же подход с очередью на PostgreSQL, без брокера сообщений.

## Роли и доступ

| Роль | Вход | Видит |
|---|---|---|
| `client` | телефон + SMS-код | публичный каталог, свой профиль, свои заказы, баланс |
| `store` | логин + пароль (argon2id), один аккаунт на магазин | только свой магазин: `store_id = principal.StoreID` в каждом запросе |
| `admin` | логин + пароль | всё, каждое действие в `audit_log` |

Доступ запрещён по умолчанию: роут без `auth.RequireRole(...)` — публичный. Группы роутов: `/v1/*` публичное, `/v1/me` любой вошедший, `/v1/store/*` только магазин, `/v1/admin/*` только админ. Объекты чужого магазина возвращают 404 (а не 403), чтобы не раскрывать их существование.

## Схема БД (основное)

`migrations/00001_init.sql`:

- `stores` (статусы `pending_activation` → `active` / `blocked` / `archived`), `users` (роль, телефон или логин, `store_id`, пол, язык, баланс токенов, параметры тела, согласие на обработку ПД).
- `refresh_tokens` — хэши, семьи токенов для обнаружения кражи.
- `categories` (зона манекена: headwear/top/bottom/shoes), `products` (обязательные поля из ТЗ, статус, причина модерации), `product_images` (три ракурса), `favorites`, `cart_items`.
- `orders` (по заказу на магазин, общий `checkout_id`; статусы `pending`, `confirmed`, `rejected`, `assembling`, `in_delivery`, `delivered`, `cancelled`; `customer_comment` — комментарий к заказу, `delivery_time_comment` — к времени доставки), `order_items` (снимок цены и названия), `order_deliveries` (улица, дом, подъезд, этаж, квартира, домофон, комментарий, координаты, ключ фото места), `order_status_history`.
- `token_ledger` (append-only, приветственный бонус один раз — уникальный индекс, одна операция на платёж/генерацию — уникальный индекс), `tariffs`, `payments` (уникальный `provider_txn_id`), `generations`, `idempotency_keys`.
- `platform_settings` (стоимость генерации = 20, бонус = 20), `audit_log` (append-only).

## Безопасность

- **Вход клиента**: только номера из разрешённых стран (`OTP_ALLOWED_PREFIXES`, по умолчанию +998), это защита от накрутки платных SMS. 6-значный код, хранится только HMAC с секретным «перцем», TTL 5 мин, 5 попыток, повтор не раньше 60 с, лимиты по телефону и IP. Одинаковый ответ для нового и существующего номера.
- **Сессии**: access-JWT (HS256, 15 мин, алгоритм зафиксирован) + refresh-токен в cookie `HttpOnly; Secure; SameSite=Lax; Path=/v1/auth`, ротация при каждом обновлении; повторное использование старого токена отзывает всю цепочку. Блокировка магазина или клиента действует сразу: refresh-токены отзываются в БД, а уже выданные access-токены отклоняются через отметку в Redis (`revoked:<user>`).
- **Перебор паролей**: лимит по логину+IP (10 за 15 мин) и общий лимит по логину (100 за 15 мин), поэтому чужой IP не может заблокировать вход админу.
- **Пароли**: argon2id (m=64 МБ, t=3), сравнение за постоянное время, фиктивная проверка при неизвестном логине (нет утечки по времени ответа).
- **Ввод**: строгий JSON (неизвестные поля → 400, защита от mass assignment), лимит 1 МБ, валидация тегами, только параметризованный SQL.
- **Файлы**: проверка сигнатуры, лимит размера и пикселей (20 Мп, защита от «декомпрессионной бомбы»), не больше `UPLOAD_CONCURRENCY` обработок на инстанс (иначе 503) и одна одновременная загрузка на пользователя, перекодирование в JPEG (удаляет EXIF/GPS), SVG/HTML отклоняются, случайные ключи с привязкой к владельцу (`media.OwnsKey`).
- **Деньги и токены**: списание/начисление в транзакции с `SELECT … FOR UPDATE`, баланс не может уйти в минус (CHECK), журнал нельзя изменить или удалить (триггеры), идемпотентность по ключу.
- **Заголовки**: CSP `default-src 'none'`, HSTS, nosniff, `X-Frame-Options: DENY`, `Cache-Control: no-store`; CORS только для перечисленных доменов.
- **Логи**: без тел запросов, query string, токенов; телефон в логах маскируется. Внутренние ошибки клиенту не показываются — только `request_id`.
- **Секреты**: только переменные окружения; в prod сервер не стартует без SMS-провайдера и с `COOKIE_SECURE=false`.

## Как найти и починить проблему

1. Пользователь/фронт сообщает `request_id` из ответа об ошибке.
2. `grep request_id=<id>` в логах (или поиск в Loki/ELK) — видны все записи этого запроса, роут, статус, длительность, текст ошибки.
3. Метрики `http_request_duration_seconds` / `http_requests_total{status=~"5.."}` по роутам показывают, что сломалось и когда.
4. Медленные SQL (>500 мс) пишет сам PostgreSQL (`log_min_duration_statement`).
5. Профиль CPU/памяти живого процесса: `curl localhost:9090/debug/pprof/profile?seconds=30` (порт не публикуется наружу).

## Развёртывание

Готовая прод-конфигурация (серверы в UZ и DE, TLS, мониторинг, бэкапы, CD) и порядок запуска: [DEPLOY.md](DEPLOY.md); действия при авариях: [RUNBOOK.md](RUNBOOK.md). Общие принципы:


- 2+ инстанса API за балансировщиком (TLS на балансировщике, `TRUSTED_PROXY=true`).
- Управляемый PostgreSQL 16 с репликой или свой с Patroni; PgBouncer в transaction mode при >5 инстансах.
- Redis с persistence (AOF), S3-совместимое хранилище, отдельный бакет для бэкапов с versioning и object lock.
- Миграции запускаются отдельным шагом деплоя (`api migrate up`) до выката новой версии; миграции пишутся обратно совместимыми (expand → migrate → contract).
