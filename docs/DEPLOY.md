# Продакшен: архитектура и первый запуск

Всё, что нужно для запуска в продакшене, лежит в репозитории: `deploy/prod/` (Docker Compose для каждого сервера, Caddy, PostgreSQL + WAL-G, мониторинг), `ansible/` (подготовка серверов), `.github/workflows/cd.yml` (выкатка). Действия при авариях описаны в [RUNBOOK.md](RUNBOOK.md).

## 1. Где что работает

Персональные и биометрические данные (база, фото клиентов и мест доставки, бэкапы, логи с IP) хранятся и просматриваются только в Узбекистане. В Германии работают сайт и сбор метрик с алертами, там персональных данных нет.

```
                 браузер клиента (UZ)
          ┌──────────────┴──────────────────────────────┐
  https://shop.uz                         https://api.shop.uz · s3.shop.uz · media.shop.uz
          │                                              │
 ┌────────▼─────────── Германия ───┐      ┌──────────────▼──────────── Узбекистан ───────────────┐
 │ edge                            │      │ app                                                   │
 │  Caddy (TLS) → web1, web2       │      │  Caddy (TLS) → api1, api2, api3 ── Redis              │
 │  Prometheus, Alertmanager→TG,   │◄─WG─►│  Loki (логи всех серверов), Grafana (только по WG)    │
 │  blackbox                       │      ├───────────────────────────────────────────────────────┤
 └─────────────────────────────────┘      │ db (primary)                    db-replica           │
                                          │  PostgreSQL 16 ──поток WAL──►    PostgreSQL 16 (hot)  │
                                          │  MinIO (фото), WAL-G, pg_dump    учебное восстановление│
                                          └───────┬───────────────────────────────────────────────┘
                                                  ▼
                                   офсайт S3 в UZ (другой ЦОД/провайдер):
                                   архив WAL + базовые бэкапы, дампы age, зеркало фото
```

Почему API тоже в Узбекистане, а не в Германии. На каждый запрос API делает несколько запросов к базе. Если API стоит в Германии, а база в UZ, каждый SQL-запрос идёт через границу (~80–100 мс туда-обратно), и каталог не уложится в цель p95 < 300 мс. Клиенты тоже в UZ, поэтому API рядом с базой даёт им самый быстрый ответ.

Серверы связаны приватной сетью WireGuard `10.77.0.0/24`: app `10.77.0.10`, db `10.77.0.20`, replica `10.77.0.21`, edge `10.77.0.30`. Внутренние порты (PostgreSQL, MinIO, метрики, Loki) открыты только на этих адресах, а firewall дополнительно режет их на публичном интерфейсе.

## 2. Размеры серверов (пик 5000 одновременных пользователей)

| Сервер | Где | vCPU / RAM / диск | Что на нём |
|---|---|---|---|
| app | UZ | 8 / 16 ГБ / 100 ГБ SSD | Caddy, 3×API (по 2 CPU, 2 ГБ), Redis 1 ГБ, Loki, Grafana |
| db | UZ | 8 / 32 ГБ / 500 ГБ NVMe (+ диск под фото) | PostgreSQL (shared_buffers 8 ГБ), MinIO, WAL-G, pg_dump |
| replica | UZ, другая стойка/ЦОД | 4–8 / 32 ГБ / 500 ГБ NVMe | горячая реплика, еженедельная проверка восстановления |
| edge | Германия | 4 / 8 ГБ / 80 ГБ | Caddy, 2×сайт, Prometheus (30 дней), Alertmanager |
| офсайт S3 | UZ, другой провайдер | ~1 ТБ с versioning | бэкапы и зеркало фото |

Расчёт: 5000 пользователей ≈ 800–1200 запросов в секунду к API в пике. Один инстанс Go-API на 2 ядрах держит такую нагрузку на чтение каталога с запасом; три инстанса дают запас на отказ одного и на выкатку. Соединений с базой 3×25 = 75 из 200, PgBouncer на старте не нужен. Подтвердить цифры нужно нагрузочными тестами `tests/load` на staging (цели: 5000 пользователей, всплеск до 10000, p95 каталога < 300 мс).

Масштабирование: добавить `api4` в `deploy/prod/app/compose.yml` и Caddyfile (или второй app-сервер за DNS), увеличить `PG_SHARED_BUFFERS` на сервере побольше.

## 3. Что нужно от вас

1. **Домен** (например, `shop.uz`) и доступ к его DNS.
2. **Четыре сервера** с Ubuntu 24.04 LTS или Debian 12 (три в UZ, один в Германии) и root-доступ по SSH-ключу.
3. **S3-хранилище в Узбекистане у другого провайдера** для бэкапов: endpoint, ключ доступа, секрет. Включите на бакетах versioning (защита от удаления).
4. **Telegram-бот для алертов**: создайте бота у @BotFather, добавьте его в группу дежурных, узнайте chat id группы (например, через @getidsbot).
5. Ключи SMS-провайдера и Click/Payme. Их добавляют в `ENV_APP`, как описано в README соответствующих модулей.
6. AI-примерка в первом релизе выключена: в `ENV_APP` стоит `TRYON_PROVIDER=off`, сайт собирается с `NEXT_PUBLIC_TRYON_ENABLED=false`. Воркер примерки, ключи Gemini/FASHN и биометрическое хранилище в UZ не нужны. Чтобы включить, укажите провайдера, `TRYON_API_KEY` и `BIOMETRIC_S3_*` в `ENV_APP`, добавьте сервис воркера и поставьте переменную окружения GitHub `TRYON_ENABLED=true`.

## 4. Первый запуск по шагам

### 4.1. DNS
| Запись | Куда |
|---|---|
| `shop.uz`, `www.shop.uz` | A → публичный IP edge (Германия) |
| `api.shop.uz`, `s3.shop.uz`, `media.shop.uz` | A → публичный IP app (UZ) |

Сертификаты Let's Encrypt Caddy получит сам при первом запуске; порты 80 и 443 должны быть открыты.

**Не ставьте CDN или второй прокси перед `api.shop.uz`.** API определяет IP клиента по последнему адресу в `X-Forwarded-For`, а Caddy перезаписывает этот заголовок. От этого зависят лимиты запросов и allowlist IP вебхуков Click/Payme. CDN можно ставить только перед `media.shop.uz` (публичные фото товаров).

### 4.2. Секреты
На своём компьютере (Windows, PowerShell, нужен Docker Desktop), в корне репозитория:

```powershell
docker run --rm -it -v ${PWD}:/w -w /w alpine:3.22 sh -c "apk add -q bash openssl age && bash deploy/prod/scripts/init-env.sh secrets-out shop.uz admin@shop.uz"
```

В папке `secrets-out` появятся `app.env`, `db.env`, `replica.env`, `edge.env`, `age-identity.txt` и `github-variables.txt` со случайными паролями. В `db.env` и `replica.env` впишите данные офсайт-S3 (строки `CHANGE-ME`), в `edge.env` впишите `TELEGRAM_CHAT_ID`. Файл `age-identity.txt` дополнительно сохраните офлайн (в менеджере паролей): без него зашифрованные дампы не прочитать. Папку `secrets-out` не коммитьте и удалите, когда перенесёте всё в GitHub.

### 4.3. GitHub
Settings → Environments → **New environment** `production` (и `staging`, если нужен):
- **Required reviewers**: вы. Тогда выкатка в production ждёт вашего подтверждения в Actions.
- **Secrets**: `ENV_APP`, `ENV_DB`, `ENV_REPLICA`, `ENV_EDGE` (содержимое файлов целиком), `AGE_IDENTITY` (содержимое `age-identity.txt`), `TELEGRAM_BOT_TOKEN`, `SSH_PRIVATE_KEY` (новый ключ только для деплоя: `ssh-keygen -t ed25519 -f deploy_key`), `SSH_KNOWN_HOSTS` (`ssh-keyscan <ip каждого сервера>`).
- **Variables**: из `github-variables.txt`, плюс `APP_SSH_HOST`, `DB_SSH_HOST`, `REPLICA_SSH_HOST`, `EDGE_SSH_HOST` (публичные IP).

Секреты хранятся только в GitHub (зашифрованы) и на самих серверах в файлах `/opt/boutique/prod/<роль>/.env` с правами 600. В репозитории секретов нет; gitleaks в CI это проверяет.

### 4.4. Подготовка серверов (Ansible)
Скопируйте `ansible/inventory.example.yml` в `inventory.yml`, впишите IP и SSH-ключи (свой и публичный `deploy_key.pub`). Запуск из WSL или Linux:

```bash
cd ansible && ansible-galaxy collection install -r requirements.yml
ansible-playbook -i inventory.yml site.yml
```

Без WSL: положите содержимое `inventory.yml` в секрет окружения `ANSIBLE_INVENTORY` и запустите Actions → **infra** (сначала с `check_only`, потом без). Плейбук ставит обновления безопасности, Docker, fail2ban, оставляет вход по SSH только по ключам, создаёт пользователя `deploy`, поднимает WireGuard между всеми серверами и настраивает firewall.

### 4.5. Выкатка
Actions → **CD** → Run workflow → `production`. Порядок: агенты мониторинга на всех серверах → db → replica → app (миграции, затем API по одному инстансу) → edge (сайт по одному инстансу, мониторинг). Дальше каждый merge в `main` после зелёного CI выкатывается автоматически: сначала staging, потом production после вашего подтверждения.

### 4.6. Первый администратор
```bash
ssh root@<app> 'cd /opt/boutique/prod/app && docker compose --profile tools run --rm -e ADMIN_PASSWORD="<длинный пароль>" migrate create-admin admin'
```

### 4.7. Проверка
- `https://api.shop.uz/readyz` отвечает `{"db":"ok","redis":"ok"}`, сайт открывается.
- В Grafana (`http://10.77.0.10:3000` через WireGuard, пользователь `admin`, пароль `GRAFANA_ADMIN_PASSWORD` из `app.env`) на дашборде «Boutique — обзор» видны все сервисы.
- В Telegram пришло тестовое сообщение: Alerts → любое правило → или временно остановите один `api` и через 2 минуты придёт `TargetDown`.
- Через сутки в S3 появились `wal/` и `daily/`, алертов `BaseBackupTooOld` нет.
- Зарегистрируйте базу персональных данных в реестре (требование закона РУз), это делает юрист.

### 4.8. Доступ к Grafana
Grafana в интернет не публикуется: она стоит в UZ рядом с логами (в них IP и маскированные телефоны) и слушает только адрес WireGuard. Чтобы открыть её с ноутбука:
1. Установите WireGuard (для Windows: wireguard.com/install), создайте ключ: «Add empty tunnel» покажет публичный ключ.
2. Добавьте ноутбук в `wg_admin_peers` в `ansible/group_vars/all.yml` (`name`, `public_key`, `ip: 10.77.0.100`) и запустите плейбук.
3. Импортируйте конфиг по образцу `ansible/templates/admin-laptop.conf.example`. После подключения откройте `http://10.77.0.10:3000`.

## 5. Как устроена выкатка

- Образы собираются в GHCR: `api:<коммит>`, `web-<окружение>:<коммит>` (адреса API вшиты в сборку сайта), `postgres:pg-<хэш>`, `backup:bk-<хэш>`. Тег образа БД зависит только от его файлов, поэтому обычный релиз не перезапускает PostgreSQL.
- Роли базы: миграции выполняются от владельца `boutique`, а API работает от `boutique_app`. У этой роли есть только SELECT/INSERT/UPDATE/DELETE, а журналы `token_ledger` и `audit_log` она может только читать и дополнять. Изменить схему или отключить триггеры она не может (права выдаёт `deploy/prod/app/grants.sql` после каждой миграции).
- `deploy/prod/scripts/deploy.sh app <тег>` на сервере: миграции (обратно совместимые) → права → `api1` → проверка `/readyz` → `api2` → `api3`. Caddy в это время отправляет запросы на живые инстансы, поэтому клиенты ошибок не видят (проверено тестом: 0 ошибок за всю выкатку). Если новый инстанс не поднялся, скрипт возвращает предыдущий тег и завершается ошибкой, CD становится красным.
- Ручной откат: Actions → CD → Run workflow с нужным коммитом в `ref`, либо на сервере `deploy.sh app <старый тег>`.

## 6. Бэкапы и восстановление (кратко)

| Что | Как часто | Куда | Хранение |
|---|---|---|---|
| WAL (журнал изменений) | непрерывно, не реже раза в 60 с | офсайт S3 `wal/`, шифрование libsodium | 7 базовых бэкапов + WAL между ними |
| Базовый бэкап WAL-G | ежедневно 02:00 Ташкент | офсайт S3 `wal/` | 7 последних |
| Логический дамп pg_dump | ежедневно 03:00 | офсайт S3 `daily/`, шифрование age | правило жизненного цикла бакета (30 дней) |
| Фото (MinIO) | непрерывно | офсайт-бакет `boutique-media-mirror` | удаления по сроку хранения доходят до копии; версии 7 дней |
| Реплика PostgreSQL | непрерывно | второй сервер в UZ | — |

RPO ≤ 1 минута, RTO ≤ 1 часа. Каждое воскресенье реплика сама скачивает последний дамп из S3, восстанавливает его во временную базу и проверяет инварианты (`restore_drill`). Если что-то из этого не работает, приходит алерт. Восстановление на момент времени описано в [RUNBOOK.md](RUNBOOK.md#pitr-восстановление-на-момент-времени).

## 7. Тест всего стека

`deploy/prod/tests/smoke.sh` поднимает все серверы на одной машине теми же скриптами, что и CD (джоб `deploy-smoke` в CI на каждый PR), и проверяет: HTTPS через Caddy, вход по SMS-коду, загрузку фото и подписанные ссылки, публичные картинки, закрытые админ-эндпоинты, сайт с CSP, все цели мониторинга и алерты, логи в Loki, архив WAL и базовый бэкап, потоковую реплику, PITR, дамп и учебное восстановление, выкатку без простоя, автоматический откат сломанного релиза и переключение на реплику.

## 8. Staging

Те же файлы и та же схема, отдельное окружение `staging` в GitHub со своими серверами и доменами (`staging.shop.uz`, `api.staging.shop.uz`, …): `init-env.sh secrets-staging shop.uz admin@shop.uz staging`. Для экономии staging можно держать на двух небольших серверах (UZ: app+db, DE: edge). В staging разрешён `APP_ENV=staging`: коды SMS пишутся в лог, а реальные SMS не отправляются.
