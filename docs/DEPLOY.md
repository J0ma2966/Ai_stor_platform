# Продакшен: архитектура и первый запуск

Всё, что нужно для запуска в продакшене, лежит в репозитории: `deploy/prod/` (Docker Compose для каждого сервера, Caddy, PostgreSQL + WAL-G, мониторинг), `ansible/` (подготовка серверов), `.github/workflows/cd.yml` (выкатка). Действия при авариях описаны в [RUNBOOK.md](RUNBOOK.md).

## 1. Где что работает

Прод работает на **одном сервере в Узбекистане**. Персональные и биометрические данные (база, фото клиентов и мест доставки, логи с IP) по закону должны храниться в UZ, поэтому сервер стоит там. Бэкапы уходят во внешнее S3-хранилище тоже в UZ, у другого провайдера.

```
                        браузер клиента (UZ)
   https://shop.uz · api.shop.uz · s3.shop.uz · media.shop.uz
                               │
 ┌─────────────────────────────▼──────────── сервер, Узбекистан ─┐
 │ Caddy (TLS, Let's Encrypt) ─┬─► web1, web2 (сайт Next.js)      │
 │                             ├─► api1, api2, api3 ── Redis      │
 │                             └─► MinIO (фото)                   │
 │ PostgreSQL 16 + WAL-G, pg_dump, еженедельная проверка дампа    │
 │ Prometheus, Alertmanager → Telegram, Loki, Grafana (по WG)     │
 └───────────────┬────────────────────────────────────────────────┘
                 ▼
  офсайт S3 в UZ (другой провайдер): архив WAL и базовые бэкапы,
  зашифрованные дампы, зеркало фото
                 ▲
  GitHub Actions раз в 5 минут проверяет сайт и API снаружи → Telegram
```

Внутри сервер устроен так же, как схема из нескольких серверов (роли `app`, `db`, `edge`, `host` в `deploy/prod/`), только все роли стоят на одной машине. Поэтому позже можно вынести базу или сайт на отдельный сервер без переделки, см. [раздел 9](#9-рост-несколько-серверов).

Внутренние порты (PostgreSQL, MinIO, метрики, Loki, Grafana, порты сайта 3001/3002) слушают только приватный адрес WireGuard `10.77.0.10`, а firewall дополнительно закрывает их на публичном интерфейсе. Через этот же WireGuard администратор открывает Grafana со своего ноутбука.

### Что вы теряете на одном сервере

| | Один сервер | Несколько серверов (раздел 9) |
|---|---|---|
| Отказ сервера или диска | сайт и API не работают, пока сервер не починят или не восстановят на новом из бэкапа: 1–3 часа | переключение на реплику за минуты |
| Потеря данных при полной потере сервера | до 1 минуты (WAL уходит в S3 не реже раза в минуту) | секунды (реплика) |
| Плановые работы на сервере (обновление ядра, перезагрузка) | простой 2–5 минут | без простоя |
| Мониторинг | на том же сервере, поэтому при его падении алерт придёт только от внешней проверки GitHub (до 5–10 минут) | с отдельного сервера |
| Стоимость и обслуживание | один сервер | четыре сервера |

Выкатка новых версий и на одном сервере идёт без простоя (инстансы API и сайта обновляются по одному). Чтобы снизить риск, берите сервер с **двумя дисками в RAID 1**: тогда выход из строя диска не останавливает работу.

## 2. Размер сервера (пик 5000 одновременных пользователей)

| | Рекомендуется | Минимум |
|---|---|---|
| CPU | 16 vCPU | 8 vCPU |
| RAM | 64 ГБ | 32 ГБ |
| Диск | 2 × 1 ТБ NVMe в RAID 1 (база, фото, логи) | 500 ГБ NVMe |
| Офсайт S3 | ~1 ТБ с versioning, в UZ у другого провайдера | |

Как распределяется: 3×API по 2 CPU и 2 ГБ, 2×сайт по 1,5 CPU и 1 ГБ, PostgreSQL (shared_buffers 8 ГБ, кэш ОС ещё ~24 ГБ), Redis 1 ГБ, MinIO, Prometheus и Loki по 1–2 ГБ. Раз в неделю проверка дампа на час занимает до 8 ГБ памяти. На минимальном сервере уменьшите `PG_SHARED_BUFFERS=4GB` и `PG_EFFECTIVE_CACHE_SIZE=12GB` в `ENV_DB`.

Расчёт: 5000 пользователей ≈ 800–1200 запросов в секунду к API в пике. Один инстанс Go-API на 2 ядрах держит такую нагрузку на чтение каталога с запасом; три инстанса дают запас на отказ одного и на выкатку. Соединений с базой 3×25 = 75 из 200, PgBouncer на старте не нужен. Подтвердить цифры нужно нагрузочными тестами `tests/load` (цели: 5000 пользователей, всплеск до 10000, p95 каталога < 300 мс). Если сервер упирается в CPU, следующий шаг — вынести базу на отдельный сервер (раздел 9).

## 3. Что нужно от вас

1. **Домен** (например, `shop.uz`) и доступ к его DNS.
2. **Сервер в Узбекистане** с Ubuntu 24.04 LTS или Debian 12 (размер в разделе 2) и root-доступ по SSH-ключу.
3. **S3-хранилище в Узбекистане у другого провайдера** для бэкапов: endpoint, ключ доступа, секрет. Включите на бакетах versioning (защита от удаления).
4. **Telegram-бот для алертов**: создайте бота у @BotFather, добавьте его в группу дежурных, узнайте chat id группы (например, через @getidsbot).
5. Ключи SMS и оплаты. В `ENV_APP` уже есть пустые `ESKIZ_EMAIL`/`ESKIZ_PASSWORD`: без них API в prod не стартует. Click и Payme включаются, когда заполнены их ключи, и тогда обязательны `CLICK_ALLOWED_IPS`/`PAYME_ALLOWED_IPS` (адреса из договора с провайдером). Перед API не должно быть CDN, иначе проверка IP не сработает.
6. AI-примерка в первом релизе выключена: в `ENV_APP` стоит `TRYON_PROVIDER=off`, сайт собирается с `NEXT_PUBLIC_TRYON_ENABLED=false`. Воркер примерки, ключи Gemini/FASHN и биометрическое хранилище в UZ не нужны. Чтобы включить, укажите провайдера, `TRYON_API_KEY` и `BIOMETRIC_S3_*` в `ENV_APP`, добавьте сервис воркера и поставьте переменную окружения GitHub `TRYON_ENABLED=true`.

## 4. Первый запуск по шагам

### 4.1. DNS
| Запись | Куда |
|---|---|
| `shop.uz`, `www.shop.uz`, `api.shop.uz`, `s3.shop.uz`, `media.shop.uz` | A → публичный IP сервера |

Сертификаты Let's Encrypt Caddy получит сам при первом запуске; порты 80 и 443 должны быть открыты.

**Не ставьте CDN или второй прокси перед `api.shop.uz`.** API определяет IP клиента по последнему адресу в `X-Forwarded-For`, а Caddy перезаписывает этот заголовок. От этого зависят лимиты запросов и allowlist IP вебхуков Click/Payme. CDN можно ставить только перед `media.shop.uz` (публичные фото товаров).

### 4.2. Секреты
На своём компьютере (Windows, PowerShell, нужен Docker Desktop), в корне репозитория:

```powershell
docker run --rm -it -v ${PWD}:/w -w /w alpine:3.22 sh -c "apk add -q bash openssl age && bash deploy/prod/scripts/init-env.sh secrets-out shop.uz admin@shop.uz"
```

В папке `secrets-out` появятся `app.env`, `db.env`, `edge.env`, `age-identity.txt` и `github-variables.txt` со случайными паролями (по умолчанию для одного сервера; для нескольких добавьте `TOPOLOGY=multi` перед `bash`, тогда появится и `replica.env`). В `db.env` впишите данные офсайт-S3 (строки `CHANGE-ME`), в `edge.env` впишите `TELEGRAM_CHAT_ID`, в `app.env` — `ESKIZ_EMAIL` и `ESKIZ_PASSWORD`. Файл `age-identity.txt` дополнительно сохраните офлайн (в менеджере паролей): без него зашифрованные дампы не прочитать. Папку `secrets-out` не коммитьте и удалите, когда перенесёте всё в GitHub.

### 4.3. GitHub
Settings → Environments → **New environment** `production` (и `staging`, если нужен):
- **Required reviewers**: вы. Тогда выкатка в production ждёт вашего подтверждения в Actions.
- **Secrets**: `ENV_APP`, `ENV_DB`, `ENV_EDGE` (содержимое файлов целиком), `AGE_IDENTITY` (содержимое `age-identity.txt`), `TELEGRAM_BOT_TOKEN`, `SSH_PRIVATE_KEY` (новый ключ только для деплоя: `ssh-keygen -t ed25519 -f deploy_key`), `SSH_KNOWN_HOSTS` (`ssh-keyscan <ip сервера>`).
- **Variables**: из `github-variables.txt`, плюс `APP_SSH_HOST`, `DB_SSH_HOST`, `EDGE_SSH_HOST`: все три равны публичному IP сервера (по совпадению адресов CD понимает, что сервер один). `REPLICA_*` не задавайте.

Внешняя проверка доступности (Settings → Secrets and variables → Actions, на уровне репозитория, не окружения): переменные `UPTIME_URLS` (`https://api.shop.uz/readyz https://shop.uz/api/healthz`) и `UPTIME_TELEGRAM_CHAT_ID`, секрет `UPTIME_TELEGRAM_BOT_TOKEN`. Раз в 5 минут GitHub проверяет сайт и API и пишет в Telegram, если они не отвечают. Это нужно, потому что встроенный мониторинг стоит на том же сервере и при его падении молчит.

Секреты хранятся только в GitHub (зашифрованы) и на самих серверах в файлах `/opt/boutique/prod/<роль>/.env` с правами 600. В репозитории секретов нет; gitleaks в CI это проверяет.

### 4.4. Подготовка серверов (Ansible)
Скопируйте `ansible/inventory.example.yml` в `inventory.yml`, впишите IP сервера (хост называется `server`, имя не меняйте) и SSH-ключи (свой и публичный `deploy_key.pub`). Запуск из WSL или Linux:

```bash
cd ansible && ansible-galaxy collection install -r requirements.yml
ansible-playbook -i inventory.yml site.yml
```

Без WSL: положите содержимое `inventory.yml` в секрет окружения `ANSIBLE_INVENTORY` и запустите Actions → **infra** (сначала с `check_only`, потом без). Плейбук ставит обновления безопасности, Docker, fail2ban, оставляет вход по SSH только по ключам, создаёт пользователя `deploy`, поднимает WireGuard (для доступа администратора к Grafana; на нескольких серверах ещё и между ними) и настраивает firewall.

### 4.5. Выкатка
Actions → **CD** → Run workflow → `production`. Порядок: агенты мониторинга → db → app (миграции, затем API по одному инстансу) → edge (сайт по одному инстансу, мониторинг). На одном сервере всё идёт по SSH на одну машину в `/opt/boutique/prod`. Дальше каждый merge в `main` после зелёного CI выкатывается автоматически: сначала staging, потом production после вашего подтверждения.

### 4.6. Первый администратор
```bash
ssh root@<сервер> 'cd /opt/boutique/prod/app && docker compose --profile tools run --rm -e ADMIN_PASSWORD="<длинный пароль>" migrate create-admin admin'
```

### 4.7. Проверка
- `https://api.shop.uz/readyz` отвечает `{"db":"ok","redis":"ok"}`, сайт открывается.
- В Grafana (`http://10.77.0.10:3000` через WireGuard, пользователь `admin`, пароль `GRAFANA_ADMIN_PASSWORD` из `app.env`) на дашборде «Boutique — обзор» видны все сервисы.
- В Telegram пришло тестовое сообщение: Alerts → любое правило → или временно остановите один `api` и через 2 минуты придёт `TargetDown`.
- Через сутки в S3 появились `wal/` и `daily/`, алертов `BaseBackupTooOld` нет.
- Зарегистрируйте базу персональных данных в реестре (требование закона РУз), это делает юрист.

### 4.8. Доступ к Grafana
Grafana в интернет не публикуется: она стоит рядом с логами (в них IP и маскированные телефоны) и слушает только адрес WireGuard. Чтобы открыть её с ноутбука:
1. Установите WireGuard (для Windows: wireguard.com/install), создайте ключ: «Add empty tunnel» покажет публичный ключ.
2. Добавьте ноутбук в `wg_admin_peers` в `ansible/group_vars/all.yml` (`name`, `public_key`, `ip: 10.77.0.100`) и запустите плейбук.
3. Импортируйте конфиг по образцу `ansible/templates/admin-laptop.conf.example`. После подключения откройте `http://10.77.0.10:3000`.

## 5. Как устроена выкатка

- Образы собираются в GHCR: `api:<коммит>`, `web-<окружение>:<коммит>` (адреса API вшиты в сборку сайта), `postgres:pg-<хэш>`, `backup:bk-<хэш>`. Тег образа БД зависит только от его файлов, поэтому обычный релиз не перезапускает PostgreSQL.
- Роли базы: миграции выполняются от владельца `boutique`, а API работает от `boutique_app`. У этой роли есть только SELECT/INSERT/UPDATE/DELETE, а журналы `token_ledger` и `audit_log` она может только читать и дополнять. Изменить схему или отключить триггеры она не может (права выдаёт `deploy/prod/app/grants.sql` после каждой миграции).
- `deploy/prod/scripts/deploy.sh app <тег>` на сервере: миграции (обратно совместимые) → права → `api1` → проверка `/readyz` → `api2` → `api3`. Caddy в это время отправляет запросы на живые инстансы, поэтому клиенты ошибок не видят (проверено тестом: 0 ошибок за всю выкатку). Если новый инстанс не поднялся, скрипт возвращает предыдущий тег и завершается ошибкой, CD становится красным.
- Ручной откат: Actions → CD → Run workflow с нужным коммитом в `ref`, либо на сервере `deploy.sh app <старый тег>`.

### Общий секрет сайта и API (`INTERNAL_API_TOKEN`)

Сайт рендерит страницы на сервере, и все его запросы к API приходят с одного IP. Общий лимит API — 600 запросов в минуту с адреса, поэтому без секрета под нагрузкой (и при сборке sitemap) сайт получал бы 429 и показывал пустой каталог. Сайт шлёт секрет в заголовке `X-Internal-Token`, и такие запросы общий лимит по IP не считают (лимиты входа, SMS и заказов действуют как обычно).

`init-env.sh` кладёт одно и то же значение в `app.env` и `edge.env`. Если окружение создано раньше: сгенерируйте `openssl rand -hex 32` и добавьте строку `INTERNAL_API_TOKEN=<значение>` и в секрет `ENV_APP`, и в `ENV_EDGE`, затем выкатите. Без переменной всё работает как раньше, только без исключения из лимита.

## 6. Бэкапы и восстановление (кратко)

| Что | Как часто | Куда | Хранение |
|---|---|---|---|
| WAL (журнал изменений) | непрерывно, не реже раза в 60 с | офсайт S3 `wal/`, шифрование libsodium | 7 базовых бэкапов + WAL между ними |
| Базовый бэкап WAL-G | ежедневно 02:00 Ташкент | офсайт S3 `wal/` | 7 последних |
| Логический дамп pg_dump | ежедневно 03:00 | офсайт S3 `daily/`, шифрование age | правило жизненного цикла бакета (30 дней) |
| Фото (MinIO) | непрерывно | офсайт-бакет `boutique-media-mirror` | удаления по сроку хранения доходят до копии; версии 7 дней |
RPO ≤ 1 минута. RTO: на одном сервере 1–3 часа (новый сервер, Ansible, восстановление из S3 по [RUNBOOK.md](RUNBOOK.md#сервер-потерян-один-сервер)); с репликой — минуты. Каждое воскресенье ночью сервер сам скачивает последний дамп из S3, восстанавливает его во временную базу и проверяет инварианты (`restore_drill`; на нескольких серверах это делает реплика). Если что-то из этого не работает, приходит алерт. Восстановление на момент времени описано в [RUNBOOK.md](RUNBOOK.md#pitr-восстановление-на-момент-времени).

## 7. Тест всего стека

`deploy/prod/tests/smoke.sh` поднимает стек теми же скриптами, что и CD (джоб `deploy-smoke` в CI на каждый PR, в двух режимах: `single` — схема прода, `multi` — несколько серверов), и проверяет: HTTPS через Caddy, вход по SMS-коду, загрузку фото и подписанные ссылки, публичные картинки, закрытые админ-эндпоинты, сайт с CSP, все цели мониторинга и алерты, логи в Loki, архив WAL и базовый бэкап, PITR, дамп и учебное восстановление, выкатку без простоя и автоматический откат сломанного релиза. В режиме `multi` ещё потоковую реплику и переключение на неё.

## 8. Staging

Те же файлы и та же схема, отдельное окружение `staging` в GitHub со своими серверами и доменами (`staging.shop.uz`, `api.staging.shop.uz`, …): `init-env.sh secrets-staging shop.uz admin@shop.uz staging`. Для staging хватит одного небольшого сервера (4 vCPU, 8 ГБ). `init-env.sh … staging` сам ставит `APP_ENV=staging` и `SMS_PROVIDER=log`: коды SMS пишутся в лог, а реальные SMS не отправляются.

## 9. Рост: несколько серверов

Когда одного сервера станет мало или понадобится переключение на реплику за минуты, те же файлы разворачиваются на четырёх серверах: `app` (Caddy, API, Redis, Loki, Grafana) и `db` (PostgreSQL, MinIO, бэкапы) в UZ, `replica` (горячая реплика и проверка дампов) в UZ в другом ЦОД, `edge` (сайт и мониторинг) в любой стране, персональных данных на нём нет. Серверы связаны WireGuard: app `10.77.0.10`, db `10.77.0.20`, replica `10.77.0.21`, edge `10.77.0.30`.

API всегда остаётся рядом с базой: если поставить его в другой стране, каждый SQL-запрос пойдёт через границу (~80–100 мс туда-обратно), и каталог не уложится в p95 < 300 мс.

Переход: `TOPOLOGY=multi` для `init-env.sh`, инвентарь Ansible из комментария в `inventory.example.yml`, переменные `*_SSH_HOST`/`*_PRIVATE_IP` для каждого сервера и секрет `ENV_REPLICA`. DNS сайта переводится на edge. Базу переносят без потери данных: на текущем сервере создайте слот (`select pg_create_physical_replication_slot('replica1');`), поднимите новый сервер БД репликой текущего (`PG_ROLE=replica`, `PRIMARY_HOST=10.77.0.10`), дождитесь синхронизации и выполните `failover.sh` (RUNBOOK, «Отказ сервера БД»).

| Сервер | vCPU / RAM / диск |
|---|---|
| app | 8 / 16 ГБ / 100 ГБ SSD |
| db | 8 / 32 ГБ / 500 ГБ NVMe (+ диск под фото) |
| replica | 4–8 / 32 ГБ / 500 ГБ NVMe |
| edge | 4 / 8 ГБ / 80 ГБ |
